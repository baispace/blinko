- 症状：`https://IP:8888` 打不开，表现为**超时**（非拒绝连接）；SSH 正常、Blinko 服务正常（HTTP 200）
- **决定性证据**：`ss -tlnp | grep 8888` → `LISTEN 101 100 0.0.0.0:8888 users:(("BT-Panel",pid=6406,fd=6))`
  - LISTEN 状态下 Send-Q = accept 队列上限(backlog)，**Recv-Q = 当前待 accept 连接数**
  - **Recv-Q(101) > Send-Q(100) = 队列爆满 = 进程卡死不再 accept** → 内核静默丢 SYN → 客户端超时
- 排除项：ufw 显示 8888 ALLOW、进程仍 LISTEN → 服务器侧正常；**不是安全组问题**（当时正因在改安全组而误判）
- 修复：`/etc/init.d/bt restart`（卡住则 `kill -9 <pid>` + `bt start`）→ 复验 Recv-Q 应为 0 → `bt default` 取登录地址
- **教训：遇到面板超时，先 `ss -tlnp` 看 Recv-Q，再查安全组**（顺序反了会白折腾）

## 性能问题根因锁定 + 修复（2026-09-26 14:30，已改代码待构建）

**根因（代码层面全部坐实，非猜测）**：
1. **无预压缩**：`app/vite.config.ts` 没有 compression 插件；`server/index.ts` 也没装 `compression`

3. **tagList 绕过批处理**：`blinkoStore.tsx:435` 的 `skipBatch: true` 让它单独发 HTTP，

**已做改动（5 个文件）**：
| 文件 | 改动 |
|---|---|
| `start.sh`（新增，dockerfile 改 `COPY start.sh ./`） | 容器启动时预生成 `.gz`；挂在容器启动流程里，容器重建也不丢（比放构建期更稳） |
| `server/index.ts` | 新增 `servePrecompressed()` 中间件，放在 `express.static` 之前：Accept-Encoding 含 gzip 且同名 `.gz` 比源文件新 → 直发 `.gz`，**零 CPU** |

| `app/src/store/blinkoStore.tsx` | 去掉 `skipBatch: true`，让 tagList 进 httpBatchLink |

**踩坑（自己写中间件时的坑，值得记）**：
- 直发 `.gz` 时 **Content-Type 必须按扩展名正确映射**。若统一给 `application/octet-stream`，
  浏览器会当成下载文件而不执行 JS/CSS → 站点整站白屏/不工作。最终按 ext 分别映射
  `.js→text/javascript; charset=utf-8` / `.css→text/css` / `.html` / `.json` / `.svg` / `.woff2`。
- `.gz` 需校验 mtime 不早于源文件，避免构建不一致时发旧压缩包。
- 路径穿越：normalize + 前缀校验（`filePath.startsWith(publicPath + sep)`）。

**效果预期**：首屏 JS 从 2.5MB 明文 → ~600KB gzip 直出；CPU 不再被压缩占用；
tRPC 首屏请求从 ~8 个降到 1-2 个 batch。

| 文件 | 改动 |
